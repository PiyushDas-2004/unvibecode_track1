# Competitor and Analogue Landscape: How Developer Tools Create Return Usage

Purpose: find the retention mechanism (what makes a developer come back to the tool) used by tools comparable to UnvibeCode. Every claim has a source URL next to it. Anything not verified is marked "unverified" or left out. Sources were checked on 2026-11-13.

---

## 1. Lockfiles as committed generated artifacts

- **npm `package-lock.json`.** npm generates it automatically whenever it modifies `node_modules` or `package.json`. The docs say it "is intended to be committed into source repositories" and exists partly to "facilitate greater visibility of tree changes through readable source control diffs" (https://docs.npmjs.com/cli/v10/configuring-npm/package-lock-json). `npm ci` is the freshness gate: if `package.json` and the lockfile do not match, "`npm ci` will exit with an error, instead of updating the package lock", and it "will never write to `package.json` or any of the package-locks" (https://docs.npmjs.com/cli/v10/commands/npm-ci).
- **Yarn `yarn.lock`.** `yarn install --immutable` will "Abort with an error exit code if the lockfile was to be modified", and this option "defaults to true on CI" (https://yarnpkg.com/cli/install). So CI fails if a developer forgot to regenerate and commit the lockfile.
- **Poetry `poetry.lock`.** The docs say "Application developers commit `poetry.lock` to get more reproducible builds" (https://python-poetry.org/docs/basic-usage/). `poetry check --lock` "Verifies that `poetry.lock` exists for the current `pyproject.toml`", and `check` validates consistency between the two files (https://python-poetry.org/docs/cli/).
- **Cargo `Cargo.lock`.** `cargo new` tracks `Cargo.lock` in version control by default. (https://doc.rust-lang.org/cargo/faq.html).
- **uv `uv.lock`.** With `--locked`, "If the lockfile is not up-to-date, uv will raise an error instead of updating the lockfile". `uv lock --check` "is equivalent to the `--locked` flag for other commands". uv does not treat a lockfile as stale just because new package versions were released. Staleness is measured against project metadata only (https://docs.astral.sh/uv/concepts/projects/sync/).
- **Go `go.mod`/`go.sum`.** "The `-diff` flag causes `go mod tidy` not to modify go.mod or go.sum but instead print the necessary changes as a unified diff. It exits with a non-zero code if the diff is not empty" (https://go.dev/ref/mod).
- **PR review.** GitHub dependency review shows manifest and lockfile changes as a "rich diff" on the Files Changed tab. The dependency review action can fail the check, and that blocks merge when the check is required (https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/about-dependency-review). Separately, marking a path `linguist-generated` in `.gitattributes` hides it by default in diffs (https://docs.github.com/en/repositories/working-with-files/managing-files/customizing-how-changed-files-appear-on-github). So a generated file can be committed without cluttering review.

**Mechanism:** a deterministic generated file is committed next to its source. A cheap "is it fresh?" command fails CI when the source changes and the artifact does not. That forces a regeneration run on every relevant change.

## 2. Snapshot testing

- **Jest.** Snapshots are stored in a `__snapshots__` directory next to the test. "The snapshot artifact should be committed alongside code changes, and reviewed as part of your code review process." A mismatch fails the test, and `jest -u` / `--updateSnapshot` regenerates the snapshots (https://jestjs.io/docs/snapshot-testing). With `--ci`, Jest does not write new snapshots. Instead "it will fail the test and require Jest to be run with `--updateSnapshot`" (https://jestjs.io/docs/cli).
- **syrupy (pytest).** It writes `.ambr` files under `__snapshots__`. `pytest --snapshot-update` updates them and deletes unused ones. By default, unused snapshots fail the suite (https://github.com/syrupy-project/syrupy).

**Mechanism:** the expected output is a committed file, so any behaviour change shows up as a readable diff in the PR. Updating it requires running the tool again.

## 3. Architecture and import rule tools

- **import-linter.** "Contracts" are declared in a committed `.importlinter` file. `lint-imports` "will error if any modules in `myproject.green` import from `myproject.blue`" (https://import-linter.readthedocs.io/en/stable/). The docs page does not describe CI setup, but a command that exits with an error is what lets it gate CI.
- **dependency-cruiser.** It validates JS/TS dependencies against rules in a committed `.dependency-cruiser.js` file, generated by `npx dependency-cruiser --init`. It reports violations "in an eslint-like format" and can output graphs (dot, mermaid, html). The project "uses itself to check on itself in its own build process" (https://github.com/sverweij/dependency-cruiser).
- **ArchUnit (Java).** Architecture rules run as plain unit tests (https://www.archunit.org/). `FreezingArchRule` records existing violations to a `ViolationStore`. After that, "Consecutive runs will then only report new violations and ignore known violations", and the store is plain text so you can "add these files to any version control system to continuously track the progress" (https://www.archunit.org/userguide/html/000_Index.html).
- **Nx module boundaries.** Constraints are defined with project tags. "If you violate the constraints, you will get an error when linting." Nx recommends adding `nx conformance:check` to CI (https://nx.dev/docs/features/enforce-module-boundaries).

**Mechanism:** rules live in a committed config and run on every PR as a pass/fail check. ArchUnit's frozen baseline is the closest analogue to a "Risk Findings" file: it reports only new findings, and the committed baseline shrinks as violations are fixed.

## 4. Dependabot and Renovate

- **Dependabot.** It is enabled "by checking a `dependabot.yml` configuration file into your repository". When it finds an outdated dependency, "it raises a pull request" (https://docs.github.com/en/code-security/dependabot/dependabot-version-updates/about-dependabot-version-updates). `schedule.interval` is required (daily, weekly, monthly, etc.). By default it keeps at most five version-update PRs open (https://docs.github.com/en/code-security/dependabot/dependabot-version-updates/configuration-options-for-the-dependabot.yml-file).
- **Renovate.** The Dependency Dashboard is an issue Renovate creates in the repo. It gives an "overview of the status of all updates", and ticking a checkbox makes Renovate open that PR or approve held updates (https://docs.renovatebot.com/key-concepts/dashboard/). `lockFileMaintenance` deletes and regenerates the lockfile, then opens a PR. It is off by default. When enabled, it runs "before 4am on monday" to "reduce noise" (https://github.com/renovatebot/renovate/blob/main/docs/usage/configuration-options.md).

**Mechanism:** the tool starts the session itself on a schedule by opening a PR that someone has to review. A single standing issue collects all pending work.

## 5. Codecov, Coveralls, SonarCloud

- **Codecov.** `codecov/project` compares whole-project coverage against the PR base. `codecov/patch` "only measures lines adjusted in the pull request" (https://docs.codecov.com/docs/commit-status). For comment noise, `require_changes` defaults to false. Setting it to `true`, `"coverage_drop"` or `"uncovered_patch"` posts a comment only under that condition. `behavior: default` edits one existing comment instead of posting new ones (https://docs.codecov.com/docs/pull-request-comments).
- **Coveralls.** It offers PR comments, a commit status, and a README badge. If you set failure thresholds, Coveralls turns the status into a check that fails when coverage falls below or drops by more than the threshold (https://docs.coveralls.io/app-notifications). I found no "only comment on changes" option on that page (unverified whether one exists).
- **SonarQube Cloud.** For pull requests, "only the quality gate conditions applying to new code are used". The gate status appears as a PR decoration, which "can be used to block the merge" (https://docs.sonarsource.com/sonarqube-cloud/improving/quality-gates).

**Mechanism:** a status check plus a single updating comment, both scoped to the diff ("patch" / "new code"). Noise controls are explicit config options.

## 6. Code intelligence and repo understanding

- **Sourcegraph.** It searches code "across all your repositories and code hosts", supports saved searches, and has code monitoring to "set up notifications for code changes that match a query" (https://sourcegraph.com/docs/code-search). Batch Changes creates PRs across many repos from a YAML batch spec. It tracks each changeset's status until merge, with a burndown chart (https://sourcegraph.com/docs/batch-changes).
- **Greptile.** "On every pull request, Greptile analyzes changes with full context." It builds "a complete graph of your codebase - every function, class, and dependency" when repos are enabled (https://www.greptile.com/docs/introduction). How the graph is refreshed is unverified.
- **CodeRabbit.** It posts a walkthrough comment "every time CodeRabbit reviews a pull request". It includes a changed-files summary, Mermaid sequence diagrams and suggested reviewers (https://docs.coderabbit.ai/pr-reviews/walkthroughs). Incremental review of each new commit is described in secondary results only (unverified against a primary page).
- **GitHub Copilot code review.** It can be requested automatically via a repository ruleset. "Review new pushes" makes it review each push, not only once (https://docs.github.com/en/copilot/how-tos/use-copilot-agents/request-a-code-review/configure-automatic-review).
- **Repomix.** `repomix --init` creates `repomix.config.json`. The default output is `repomix-output.xml`. (https://repomix.com/guide/configuration). Whether the docs recommend committing the config is unverified.
- **Swimm (key analogue).**
  - Docs are files in the repo: "All docs will be saved under the .swm folder once the docs are committed to the repository". Web-app docs are saved as `.swm/<name>.sw.md` (https://docs.swimm.io/getting-started-guide/creating-a-doc). Swimm moved from JSON `.swm` files to Markdown `sw.md` partly because JSON changes were "hard to review" (https://swimm.io/blog/docs-as-code-understanding-swimm-sw-md-markdown-format/).
  - Auto-sync "automatically keeps code snippets up to date with routine code changes via your CI". When a change is "impactful enough that Swimm oversight is needed", the "Swimm verification check will fail". Depending on configuration, it either blocks the commit/PR or opens an issue with a deadline (https://docs.swimm.io/features/keep-docs-updated-with-auto-sync). The check covers "code snippets, smart tokens, and smart paths" (https://swimm.io/?p=772).
  - It uses line markers, token references, change size and git history (so shallow clones do not work). Moved, unchanged code is synced silently; deleted code needs a human (https://swimm.io/blog/how-does-swimm-s-auto-sync-feature-work/).
  - The GitHub App adds a "Swimm Verify" check to PRs and comments when docs are out of date. "Approve Auto-sync" commits the fix to the PR, and this can be set to automatic. An option (off by default) limits the check to files changed in the PR, and doc comments can be disabled (https://docs.swimm.io/continuous-integration/github-app).

**Mechanism (Swimm):** an artifact coupled to specific code is committed in the repo. A PR check compares it with the new code. Small drift is fixed by a bot commit. Large drift fails the check and needs a person. The tool runs on every PR because the committed artifact can go stale.

## 7. CODEOWNERS, git blame, git log

- A `CODEOWNERS` file in `.github/`, the root or `docs/` means owners "are automatically requested for review when someone opens a pull request that modifies code that they own". Branch protection can require their review (https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).
- `git blame` "Annotates each line in the given file with information from the revision which last modified the line" (https://git-scm.com/docs/git-blame). `git log --follow` continues "the history of a file beyond renames" (https://git-scm.com/docs/git-log).

**Mechanism:** a small committed file drives routing on every PR. Committed files also gain history that developers query later.

## 8. pre-commit framework

`.pre-commit-config.yaml` goes in the repo root. `pre-commit install` adds the git hooks. `pre-commit run --all-files` is "useful ... if you are using pre-commit in CI". `pre-commit autoupdate` updates hook versions to the latest tags. pre-commit.ci can autofix PRs and "periodically autoupdates your configuration" (https://pre-commit.com/).

**Mechanism:** a committed config runs on every local commit and in CI. A bot opens recurring autoupdate PRs.

## 9. Code search as an adoption metric

- **GitHub syntax.** Legacy code search has `filename:` ("matches code files with a certain filename"). Filename-only searches do not need a search term (https://docs.github.com/en/search-github/searching-on-github/searching-code). The current syntax uses `path:` with globs, and a regex such as `path:/(^|\/)README\.md$/` matches an exact filename (https://docs.github.com/en/search-github/github-code-search/understanding-github-code-search-syntax).
- **Limits that skew counts.** Only the default branch is searched, only files under 384 KB, and repos inactive for a year are excluded (legacy docs above). The REST `GET /search/code` endpoint returns `total_count`, allows 10 requests/minute, and caps results at 1,000 (https://docs.github.com/en/rest/search/search#search-code).
- **Real example.** A GitHub issue states: "A GitHub code search finds 432 public repositories already committing an actions.lock". The query and date are not given (https://github.com/getplumber/plumber/issues/542).
- **Documented method.** Sourcegraph Code Insights recipes count repos containing a file over time. Examples: `select:repo file:yarn.lock` under adoption, `repohasfile:CODEOWNERS select:repo`, and `file:\.circleci/config.yml select:repo` for CI tooling adoption (https://7.4.sourcegraph.com/code-insights/references/common-use-cases.md).

**Implication:** a committed file with a distinctive name, such as a fixed path or header, can be counted publicly. Counting needs care because of the limits above.

## 10. Published data on developer-tool retention

- Murphy-Hill, Butler and Savelieva studied Microsoft's 2026 rollout of Copilot CLI and Claude Code (https://arxiv.org/abs/2607.01418). They define retention as activity on at least 5 of the first 14 days, to separate "tried and stayed" from "tried and abandoned". Findings:
  - "The factors that predict initial use are not those that predict retention."
  - Peer use raised trial odds sharply: +216% at the skip-level, +54% among reviewer peers. Its link to retention was weaker (+66% at the top skip-level band).
  - Retention rose with prior PR volume (+31% at 2+ PRs/week).
  - Prior IDE Copilot use predicted lower retention (−12% to −15%). The authors suggest a familiar alternative makes it easier to fall back.
  - Source: arXiv PDF of 2607.01418.
- I found no credible published dataset on "CLI tools used once" rates.

## Transferable retention mechanisms

1. **Committed artifact regenerated on change.** Every clone carries the tool's output and name, and a diff appears in PRs. Demonstrated by: lockfiles, Jest/syrupy snapshots, Swimm `.swm/*.sw.md`.
2. **Cheap freshness check that fails CI when the artifact is stale.** This forces a rerun on each relevant change. Demonstrated by: `npm ci`, `yarn --immutable`, `uv lock --check`, `poetry check --lock`, `go mod tidy -diff`, Jest `--ci`, Swimm Verify.
3. **Bot auto-fixes small drift and escalates large drift to a person.** Demonstrated by: Swimm Auto-sync, pre-commit.ci autofix, Renovate lockFileMaintenance.
4. **Diff-scoped reporting (only new or changed code).** This keeps output relevant on every PR. Demonstrated by: Codecov patch status, SonarQube Cloud new-code gate, Swimm "changed files only", ArchUnit FreezingArchRule.
5. **Committed baseline of known findings that only shrinks.** Old findings stop being noise, and regressions are caught. Demonstrated by: ArchUnit ViolationStore, snapshot files.
6. **Committed rules config that runs as a PR status check.** Demonstrated by: import-linter, dependency-cruiser, Nx boundaries, pre-commit, CODEOWNERS.
7. **Tool-initiated sessions on a schedule.** A PR or issue appears without the developer remembering to run anything. Demonstrated by: Dependabot `schedule.interval`, Renovate, `pre-commit autoupdate` via pre-commit.ci.
8. **One standing, self-updating summary instead of repeated posts.** Demonstrated by: Renovate Dependency Dashboard, Codecov `behavior: default`, CodeRabbit walkthrough.
9. **Explicit noise controls in config.** Demonstrated by: Codecov `require_changes`, Renovate weekly lockfile window, Swimm comment toggles, Dependabot open-PR limit.
10. **Review routing from a committed file.** The tool's output decides who must look at a PR. Demonstrated by: CODEOWNERS, CodeRabbit suggested reviewers.
11. **Distinctive committed filename as a public adoption counter.** Demonstrated by: GitHub `filename:`/`path:` search, Sourcegraph `select:repo file:yarn.lock`, the actions.lock count.
12. **Peer visibility drives trial, and work cadence drives retention.** Output visible to reviewers spreads the tool, and output tied to PR flow keeps it. Demonstrated by: Microsoft CLI study, dependency review rich diff, PR-comment tools.
